# 豁免与例外（R10 的执行细则）

规则存在的目的是**可维护**，不是自证。下面这些情况下硬套行数/目录规则反而有害。

## 判定流程（三问）

1. 这个产物**会被长期维护、被别人改**吗？→ 会，不豁免
2. 它的形态**本身就是交付物**（一个 HTML 文件、一张图、一个脚本）吗？→ 是，豁免 R3/R4
3. 拆开之后**更难读**吗？（声明式 UI、数据表、生成的代码）→ 是，按对应条款折算

## 豁免清单

| # | 类别 | 覆盖规则 | 理由 |
|---|---|---|---|
| E1 | 一次性交付物：单文件 HTML demo、SVG 图、设计原型、p5js / manim / ascii 渲染脚本 | R2、R3、R4 | 产物即文件，拆开就无法交付 |
| E2 | 生成代码：protobuf、OpenAPI codegen、ORM migration、资源索引、图标字体 | R2、R3 | 人是读者不是作者，改了会被覆盖 |
| E3 | 测试代码 | R2（测试函数可长） | 一个用例把前置/断言写全，比拆散更好读；R3 仍建议遵守 |
| E4 | 数据/常量表：字典、文案表、lookup table | R2、R3 | 衡量单位是"数据条数"不是"逻辑行数" |
| E5 | 存量文件（本次未修改） | R3 | 不强制重写；改动时只要求"不得净增长" |
| E6 | 声明式 UI：ArkUI `build()`、React JSX 的组件树 | R2 | 按"抽出子组件后"的行数折算，不按原始缩进块计 |
| E7 | 技能/脚手架里的教学示例 | R2、R3、R4 | 示例讲的是用法，落地到项目时必须按规范重写 |

## 不予豁免（永不放行）

- 新写的**生产模块**套用 E1——"先写着，回头拆"不会发生
- 被修改文件的**净增长**（可以不变长，不许更长）
- 空 `catch`、吞异常（R6）
- 跨模块深层 import（R4）
- 为了过 linter 压缩代码（R2 的规避条款）

## 如何声明

文件第一行（或注释块首行）：

```
// standards-exempt: E1 单文件演示页，交付形态即为一个 HTML
```

- 一个文件**只允许一条**，多处豁免写在一起
- 理由必须能被 reviewer 验证："E2 由 protoc 生成"可以；"临时"、"先这样"不行
- 豁免是**声明**不是**许可**：评审可以拒绝，agent 不得自行批准自己的新生产代码

## 常见误判

| 情况 | 正确做法 |
|---|---|
| 一个 700 行的 `util.ts` 说是"工具库，天然杂" | 按主题拆成 `string.ts` / `date.ts` / `file.ts` |
| `build()` 太长就把语句挤成一行 | 抽 `@Builder`，不是压缩 |
| 页面文件 900 行，说"页面就是一个整体" | 页面 = 入口 + 子组件，子组件拆目录 |
| 迁移期保留旧文件，新增功能也写进去 | 旧文件冻结，新功能新文件 |
